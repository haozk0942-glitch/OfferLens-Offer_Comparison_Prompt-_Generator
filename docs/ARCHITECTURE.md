# OfferLens 项目架构与节点审阅笔记

更新时间：2026-10-24。依据当前代码核对；“已实现”表示存在实现，不代表经过真实用户或职业预测有效性验证。

目标人群：应届生与初职求职者。中文、手机优先、无需登录。

状态：已实现 / 部分实现 / 计划·MVP增强 / 后续可选 / 暂不纳入。

## 最新主流程

自我画像 → Offer 信息 → 生成 Prompt → 用户自行粘贴到外部 AI；本地规则比较保留为辅助。新增 cities[]、背景信息、流动意愿、具体外派和出差字段。旧字段 city 自动迁移；下面数据实体表是初始模型概览，新增字段以 B12 / C10 / C11 / G 层及 model.js 为准。

## 1. 全局架构

~~~mermaid
flowchart TD
  A[入口：开始填写或体验示例] --> B[用户画像]
  A --> C[Offer 与岗位画像]
  B --> D[输入处理与硬约束检查]
  C --> D
  D --> G[六维效用与加权计算]
  G --> H[未知范围与结论门槛]
  H --> E[结果解释与行动清单]
  E --> I[修改画像、权重或岗位信息]
  I --> D
  B <--> F[本地草稿与 JSON 备份]
  C <--> F
  J[未来：经历 AI 提取] -.用户确认后.-> B
  K[可选：MBTI 与八字探索] -.仅引导现实偏好确认.-> B
~~~

## 3. 数据实体与关系

| 实体 | 当前字段 | 当前用途 | 后续扩展 |
| --- | --- | --- | --- |
| Profile 用户画像 | stage、goal、city、minMonthly、targetMonthly、maxHours、liked、disliked、mbti、weights | 底线、经济目标、权重、经历回顾 | 结构化偏好、证据和用户确认 |
| Offer 岗位机会 | id、name、role、city、salary、months、bonus、hours、tasks、source、五项评价 | 一个机会的条件和自评 | 实际任务、通勤、团队、逐字段证据 |
| Evaluation 计算结果 | annual、gates、unknown、contributions、low、high、coverage、score、eligible | 临时计算、结果展示 | 翻转阈值与比较理由 |
| Draft 当前草稿 | profile、offers、example | 一个画像关联 2—8 个机会；本地单份保存 | 多组比较和版本 |
| Evidence 证据 | 尚无独立实体 | 目前只有整份 offer 的 source | 字段、来源、日期、状态、合理范围 |
| DecisionSnapshot 决策快照 | 尚未实现 | 当前修改会覆盖草稿 | 输入与规则版本、选择、理由、复盘 |

Evaluation 不单独保存，每次查看结果按当前草稿重算。source 目前不改变评分。目标和经历不会自动调整权重；城市和工时目前主要用于底线，不自动推导生活评分。

1. 用户画像是否足够具体？优先补任务兴趣、工作方式还是现实责任？
2. 第一版是否保留“用户给岗位打分”，还是增加问题和证据辅助打分？
3. 哪些条件是硬底线，哪些应该允许权衡？
4. 经济维度达到目标即封顶是否符合预期？是否需要分段效用？
5. 当前只有所有机会完整且无底线问题时才给领先结论，是否应改为只比较合格机会？
6. 已知项参考分可能受缺失信息结构影响，是否需要更突出范围或隐藏参考排名？
7. MBTI 和八字是否作为独立趣味入口？两者均不直接计分。
8. 一周内优先做动态追问、证据管理还是结果取舍解释？建议先画像确认与取舍解释。
